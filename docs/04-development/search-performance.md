# 检索性能与规模上限（2026-11 实测）

> 回答两个问题：知识条目变多后**查询会不会变慢**、**效果会不会变差**？以及要不要学 Hermes 换 SQLite。
> 结论先行：**现在的瓶颈是内存与启动，不是排序质量**；本次热路径优化把 5k 规模的单次查询从 ~10ms 降到 ~4ms，20k 从 ~57ms 降到 ~29ms。**但规模超过 20k 后纯内存不再可行**（100k 时 285ms / 1.1GB / 每次启动重建 11.5s），此时应换**派生 SQLite 索引**（可删可重建，文件仍是唯一真相），并按业务域分库。分档与前置条件见 §5。

## 1. 现状实现与复杂度

`src/search.ts` 的 `KnowledgeIndex` 是纯内存倒排索引：

- 写入：`add()` 对 title×3、tags×2、summary×2、body×1 分词（CJK unigram + bigram），得到 `token → tf`，同时维护 `token → (id → tf)` 的 postings 与总长度。
- 查询：`tokenize(query)` → 每条查询 token 求 IDF（BM25）→ 遍历该 token 的 postings 累加分数 → 过滤/加权（类型、时效、标题、本地优先、`min_score`）→ 取前 `limit`。

单次查询的复杂度：

```
O(N)            可见性/状态过滤（每个 entry 查一次 scope）
+ O(Σ df_t)     postings 遍历，df_t 是该 token 的文档频率
+ O(C · K)      前 K 名选择（K = limit，很小）
```

`Σ df` 是主项：查询 token 越常见、条目越多，候选越多。5k 条目、20 条查询平均触碰 ~27k 候选，20k 条目 ~107k 候选。

启动是另一条成本线：`KnowledgeStore.load()` 每次启动**重新读取并解析所有 Markdown**，再重建索引；watcher 之后只增量 `refreshPath`，不会全量重建。

## 2. 实测数据

合成语料：确定性 PRNG + Zipf 词频（长尾更接近真实中文语料），每条 title 2–3 词、summary 6–9 词、body 3–6 段（平均 227 字符）。20 条两词查询，预热 1 轮后测 2 轮，取中位数/95 分位。Node v24.22.1 / Windows。

| 规模 | 优化前 p50 | 优化后 p50 | 优化后 p95 | 索引堆内存 | 索引构建 | FTS5 p50 | FTS5 体积 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 1k | 1.32 ms | **0.53 ms** | 1.02 ms | ~24 MB | 0.10 s | 0.94 ms | 2.5 MB |
| 5k | 10.58 ms | **3.94 ms** | 5.75 ms | ~90 MB | 0.50 s | 3.75 ms | 13.3 MB |
| 20k | 57.03 ms | **29.23 ms** | 38.16 ms | ~190 MB | 2.1 s | 14.83 ms | 50.3 MB |
| 50k | — | **107.13 ms** | 121.82 ms | ~647 MB | 5.6 s | 33.99 ms | 129.7 MB |
| 100k | — | **284.98 ms** | 358.50 ms | ~1107 MB | 11.5 s | 63.40 ms | 256.2 MB |

> 50k / 100k 只测了优化后的内存版（50k 起单次查询已不可用于「每回合预检 + 检索」）。这两个规模下的堆内存是**硬约束**：DSH Desktop 是常驻进程，1.1 GB 索引会显著挤压主进程与渲染进程的余量。

FTS5 侧：`fts5(id UNINDEXED, tokens, tokenize="unicode61")`，把同一套分词结果用空格拼成 `tokens` 列，查询 `tokens MATCH '"词1" AND "词2"' ORDER BY bm25(...)`。注意这是我们**自己分词后喂给 FTS5**，不是让 FTS5 处理中文原文（`unicode61` 不切中文，`trigram` 又不支持 2 字查询）。

读法：

- 1k 以内两边都在亚毫秒，谁都不影响体验。
- 5k 是分水岭：内存版 ~4ms，一次预检 + 一次 `memory_search` 约 8–12ms，可接受。
- 20k 起内存版进入 ~30ms/次；此时真正的压力是**堆内存 ~190MB**（每个条目一份 token→tf Map）和**启动解析 2s+**。
- 50k / 100k 是断崖：查询 107ms / 285ms，堆 647MB / 1.1GB，启动重建 5.6s / 11.5s——**不是「慢一点」，而是不能常驻**。
- 合成语料是「稠密」压力测试：所有文档共享约 30 个高频词，候选量 ≈ 5×N。真实语料词表更长、df 更低，数字应更好看；但**增长趋势**一致。

## 3. 本次优化（行为不变的纯热路径）

1. **时间戳预解析**：`temporalTimesOf()` 在建索引时把 `valid_from` / `expires_at` / `last_verified` / `updated_at` 解析为 epoch ms，存进 `IndexEntry`；查询用 `temporalStateFromTimes()` 直接比较，不再对每个候选 `Date.parse` 4 次。这是原实现最大的隐性热点（10 万候选 ≈ 40 万次日期解析）。
2. **标题归一化缓存**：`titleNormalized` 建索引时算一次，查询里 `includes(normalizedQuery)` 直接比，不再逐候选 `NFKC + toLowerCase`。
3. **前 K 名选择取代全量排序 + 全量命中对象**：原实现对每个过线候选都生成 `KnowledgeHit`（含 `makeSnippet` 的字符串扫描）再整体排序；现在只维护 limit 个轻量 `{id, score, temporal}`，最后只为入选的 8 条生成 snippet 与命中对象。
4. **`nowMs` 统一**：新鲜度衰减改用 `filters.nowMs`（缺省 `Date.now()`），测试可以真正固定「现在」，不再有「时效用假时间、新鲜度用真时间」的割裂。

排序语义完全保留：先按分数降序，平分按 id 降序；新增测试 `returns the same top-limit slice as a full ranking would` 锁定「截断不改变前 K 名」。

没有做的事（有意）：

- 没有给高频 token 设 df 上限——那会直接伤召回，属于产品决策，不是性能优化。
- 没有把 `allowed` 过滤缓存成「每工作区 id 集合」——它只占 O(N) 的一次 Map 查询，当前 < 1ms；引入缓存会让 watcher/配置热更新多一条失效路径。
- 没有引入新依赖。

## 4. 「数量多了效果会不会变差」

拆成三层看：

**4.1 排序质量：基本稳定。** BM25 的 IDF 由「df / N」决定；同一主题的文档一起增长时 df 与 N 同比例上升，IDF 趋于常数（实测榜首分数 1k→100k 仅从 ~3.7 升到 ~4.0）。所以「越查越差」在这个量级不成立。

**4.2 `min_score` 的绝对阈值会漂移。** 如果新增文档**不**覆盖旧词（df 不变而 N 变大），这些词的 IDF 会涨，分数整体抬高，`min_score: 1.0` 的相对严格度就下降——表现为「预检开始塞不相关命中」。当前默认 `min_score: 1.0`（预检），在 1k–20k 的合成语料里没有观察到明显漂移；但这是一个**应该在真实 Hub 里用引用率验证**的假设，而不是可以忽略的细节。若真出现漂移，改成「相对阈值」（如 `topScore × ratio`）比调大绝对值更稳。

**4.3 竞争变激烈。** 条目越多，同一查询的「近似命中」越多，8 个席位里更容易混入弱相关条目。这不是检索算法退化，而是**知识库卫生问题**：重复与近重复条目该合并。我们已有 `memory_duplicates` + `merge` 与夜间维护，规模上去后应把「近重复对数」当作健康指标看，而不是调检索参数。

## 5. 规模分层与索引选型

先给结论：**按规模分档，不按偏好选型。**

| 规模 | 方案 | 理由 |
| --- | --- | --- |
| ≤ 5k | 内存倒排（现状） | 单查询 < 4ms，索引 < 100MB，零依赖，最省心 |
| 5k–20k | 内存倒排 + 可选持久化快照 | 查询 4–30ms 可接受；用快照把启动从 2s+ 降到打开即用；堆内存 90–190MB 需观察 |
| > 20k | **派生索引**（SQLite 或紧凑倒排） | 100k 时内存版 285ms/1.1GB，不可用；SQLite 63ms/256MB，体积与延迟都可控 |
| > 100k | 分库（按业务域/核心分 Hub）+ 派生索引 | 单索引只承载「一个业务域」；跨域靠金字塔回退与 `core` 参数 |

### 5.1 为什么 >20k 必须离开纯内存

50k：堆 ~647MB、单查询 107ms、启动重建 5.6s。

100k：堆 ~1107MB、单查询 285ms、启动重建 11.5s。

DSH Desktop 是常驻进程，1.1GB 只是索引；再叠加会话上下文、面板与渲染进程，OOM 风险与 GC 停顿都不可接受。更致命的是**启动重建**：每次重启都要把几万份 Markdown 重新读一遍、分一次词。

### 5.2 三种候选，按「语义保真度」排序

1. **SQLite 存 postings 表**（`token, id, tf` + `docs(id, length, status, scope, times)` + `meta(df, N, totalLength)`），查询按 token 批量取行，**BM25 打分仍在 JS 里跑现有实现**。语义与现在**逐位一致**，`min_score` 不需要重标定；代价是 100k 时约 600 万行、体积 ~300MB、首次构建 10–20s（之后增量）。
2. **SQLite FTS5 取候选 + JS 重排**：FTS5 只负责「哪些文档含这些词」，但要注意 FTS5 的 `MATCH a AND b` 是**交集**，而我们现在是**并集**（只命中一个词的文档也参与打分）。要保语义得出 `a OR b` 再在 JS 里算 tf/df，还需要一张 `df` 表；实现比方案 1 复杂，且 FTS5 的 `bm25()` 与我们的系数不同，不能直接当分数用。
3. **紧凑内存倒排**：token 字符串驻留 + 数值 id + `Int32Array` postings，目标把 100k 的 1.1GB 压到 ~250–350MB、查询降到 ~60–80ms，依赖不变但工程量大、正确性风险高（要重写索引结构）。

**建议方案 1**（postings 表）：唯一能保证「换存储不换排序」的选项，也正是「SQLite 只做派生索引」的合理解释。方案 3 可以作为将来减少依赖的备选。

### 5.3 采纳前置条件（都满足才做）

- 真实 Hub 条目数 **> 20k**（或单次预检 + 检索 > 100ms）；
- `engines.node` 抬到 **≥ 22.5**（`node:sqlite`），且接受「无 SQLite 时回退内存」的双实现；
- 索引文件固定放 `records/index.sqlite`，**可随时删除重建**，不参与备份、不进 git；
- 启动校验用「条目数 + 最近 mtime + 索引版本」三件套，不匹配就后台重建（重建期间可先用内存索引服务）。

### 5.4 分库比换引擎更重要

100k 条塞进一个索引，无论什么引擎，单次查询都要扫大量候选。真实业务天然有边界：按**客户 / 业务线 / 项目**拆成 core workspace，每个索引 5k–20k，查询先本域、再金字塔回退。这是我们已经有的能力（多 core + `core_id` 上级链），在规模上比任何引擎优化都更有效。

## 6. 还没测的

- 真实语料（当前 Hub 的实际条目）上的数字与榜首分数分布；
- `KnowledgeStore.load()` 全量启动耗时（20k 条文件读取 + YAML 解析），预计是下一个瓶颈；
- 多核心 Hub 的预检并发（金字塔回退可能一次查 2–3 个索引）；
- 面板列表接口在大库上的耗时（它走 `records()` 全量 + 序列化）；
- 候选积压（`pending/` 上千条）对启动与面板的影响——**大批量萃取时这会是先撞上的墙**。

npx vite-node scripts/bench-search.ts --sizes 50000,100000   # 断崖区（吃内存，慎跑）

## 8. 派生 SQLite 索引实测（2026-11-08）

实现见 [proposal-derived-index.md](../03-openspec/proposal-derived-index.md)。设计是 **FTS5 取候选 + 同一份 JS 精排**：把自家分词结果按空格拼成 `tokens` 串写进 contentless FTS5，中文词元可精确命中；查询先 `MATCH ... OR` 取 `index_candidate_limit`（默认 2000）个 rowid，再回表、由 `rankScored` 精确打分。

| 条目 | 内存 p50 | 派生索引 p50 | 纯 FTS5 命中 | 内存堆 | 索引磁盘 | 重建 |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 20k | 39 ms | 112 ms | 17 ms | ~210 MB | 50 MB | 3.0 s |
| 50k | 158 ms | 231 ms | 45 ms | ~600 MB | 124 MB | 8.5 s |
| 100k | 352 ms | 399 ms | 88 ms | ~1.1 GB | 246 MB | 18.7 s |

要点：

- 纯 postings 方案已被否掉：100k 单查询 p50 1.5–2.4 s（50 万行搬进 JS + 逐行取元数据）。
- 派生索引不是延迟优化，**是内存上限方案**：100k 用 ~250 MB 磁盘换掉 ~1.1 GB 常驻堆，延迟只慢 10–15%。
- 命中数 ≤ 候选上限时与内存索引逐位一致；超过上限是两阶段检索，synthetic 最坏语料 recall@8 = 0.925（候选 2000），调大 `index_candidate_limit` 可换精度。
- 因此 `storage.index: auto` 的阈值定在 **30k**：30k 以下内存更快，30k 以上用磁盘换内存。

复现：

```powershell
npx vite-node scripts/bench-search.ts --sizes 20000,50000,100000 --candidates 2000
```
