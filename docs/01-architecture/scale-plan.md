# 规模化与业务萃取：架构预案

> 背景：真实 Hub 是**多年业务积累**，规模远大于开发环境；这个项目的主目标不是「记聊天」，而是把业务资料**萃取成可复用的判断**（决策、约束、流程、方法），再蒸馏上推。
> 这份文档把「规模」拆成三条互相独立的成本线，给出分档方案与阶段计划。数字来自 [search-performance.md](../04-development/search-performance.md)。

## 1. 三条成本线，别混在一起谈

| 成本线 | 现在的断点 | 真实影响 |
| --- | --- | --- |
| 检索（读） | 20k 条起单查询 30ms、堆 190MB；100k 条 285ms、1.1GB、启动重建 11.5s | 桌面端常驻进程扛不住；预检每回合都要查 |
| 入库（写） | 候选只能一条条 `memory_propose`；`pending/` 上千条时启动解析与面板列表都会变慢 | 多年资料根本进不来，或进来后审不完 |
| 蒸馏（整理） | `distill` 按工作区定时跑、每次最多 3 个会话；`memory_duplicates` 是两两比较 | 规模上去后「整理」本身成为瓶颈；重复条目污染检索 |

结论：**先解决「入库 + 审批吞吐」，再解决「检索分片」**。查询慢一点还能忍，资料进不来、审不完，项目就没有产出。

## 2. 目标形态

```
业务域 A（core workspace） ──┐
  业务域 B（core workspace） ─┼─→ 父核心（跨域共性：方法论、公司级约束）
  业务域 C（core workspace） ─┘
        │
        └── 每个域自己的索引（5k–20k），查询先本域、再金字塔回退
```

三条原则：

1. **按业务边界分库，不按时间分库**。一个客户/业务线/项目 = 一个 core 或子工作区；单库 5k–20k 是舒适区。跨域共性靠已有的 `core_id` 上级链上推，而不是塞进一个巨型库。
2. **索引是派生物，文件仍是唯一真相**。超过 20k 时引入 `records/index.sqlite`（postings 表 + JS 打分），随时可删可重建；没有 SQLite 时回退内存索引。
3. **候选分批，人按批审**。萃取的人机界面单位是「批次」，不是「单条」。

## 3. 入库：批量萃取流水线

### 3.1 批次模型

- **批次（batch）** = 一个来源目录 + 一个业务主题，例如 `2021-客户A-实施`。
- 每批写一份 `batch.yaml`（放在**工作区**里，不进 Hub 存储）：`id`、`title`、`source_dir`、`domain`/`project` 作用域、`chunk_size`、`status`。
- 批次切成 **chunk**（建议 10–20 个文件或 ~20k 字）；**一个 chunk = 一个会话（或一次子 agent 任务）**。
- 每个 chunk 的产出是 5–15 条候选，而不是「一段摘要」：一条知识 = 一个可复用判断（我们已有九类格式）。

### 3.2 每个 chunk 的提示词骨架

1. 读 chunk 内文件，先列「这份材料能回答哪些以后会再问的问题」；
2. 只抽**可复用**的判断：决策与理由、约束与边界、踩过的坑、可复制的流程；
3. 每条 `memory_propose`，`type` 从九类里选，`scope` 按 batch 配置，`source_refs` 必须指回原文（`file:<相对路径>#Lx`），`tags` 带 `batch:<id>`；
4. **不 commit**，不做整篇摘要，不为凑数拆条；
5. 结束时报「本 chunk 产出 N 条 + 覆盖了哪些问题」。

### 3.3 批次状态机

`draft → extracted → reviewed → distilled → archived`

- `extracted`：chunk 全部跑完，候选都在 `pending/` 且带 batch 标签；
- `reviewed`：人已逐批批准/拒绝（面板按 `tags:batch:<id>` 过滤，勾选批量，单次 ≤50）；
- `distilled`：本批的共性已上推到父核心；
- `archived`：来源目录可以移走。

### 3.4 为什么必须分批

一个会话读不完几百份文档；上下文与产出质量都会崩。分批也让失败可重试（重跑一个 chunk 不影响其他批），并让「这一批用了哪个模型/提示词」可追溯。

## 4. 审批：吞吐与质量

现状：`memory_commit` 一次一条、面板批量 ≤50/次。5k 条候选 = 100 次批量点击，且每次要点开看。

改进顺序：

1. **先过滤再给人看**：批次导入完成后先跑 `memory_duplicates`（按类型 + 作用域分组），把近重复标出来；`memory_propose` 对**精确重复**已拒绝，但语义重复仍会进候选。
2. **面板按批次分组**：显示「本批 137 条，重复 12 条，风险标记 3 条」，默认只让人看非重复项。
3. **分级审批**：低风险（`knowledge`/`process`、无风险标记、非重复）可 50 条一批快速过；`decision`/`constraint` 必须逐条看（这些是以后会被引用的硬结论）。
4. **不让模型自批**这条硬规则不变；变的只是「人看得更快」。

### 4.1 候选量的现实校准

一条知识需要 3–5 份材料支撑才不会碎片化。若来源有 2,000 份文档，目标应是 **400–800 条候选**，不是 5,000 条。抽得越碎，审批越不可能完成，检索也越差（8 个席位被同义碎片占满）。

## 5. 蒸馏：从「逐条上推」改成「按主题上推」

- L1（本域）：批次入库时就落在自己的 core/项目库。
- L2（跨域共性）：按**主题**抽样——同一 `type` + 相近 `tags` 的 20–50 条一起读，产出「共性结论 + 差异点」，而不是逐条复制上推。
- L3+：季度级人工整理（`memory_consolidate` + 面板），不做自动。
- 去重发生在**上推之前**：先 `memory_duplicates` + `merge`，再蒸馏，否则父核心会被重复条目灌满。

## 6. 检索：分档与触发条件

| 规模 | 方案 |
| --- | --- |
| ≤ 5k | 现状（内存倒排） |
| 5k–20k | 内存倒排 + 持久化索引快照（省启动重建） |
| > 20k | `records/index.sqlite`：postings 表 + JS BM25，语义与现在逐位一致 |
| > 100k | 分库；单库回到 5k–20k 区间 |

触发条件、三种候选方案的取舍见 [search-performance.md §5](../04-development/search-performance.md)。

## 7. 阶段计划

### P0：让「入库」可规模化（不做检索改造）

- **[已完成]** skill 里的「批量萃取」工作流：`batch.yaml` 清单、chunk 规则、提示词骨架、批次状态机；模板 `docs/07-templates/batch-extraction.md`。
- **[已完成]** 面板按 `tags:batch:<id>` 聚合与筛选（只读视图，不新增写端点）；列表只返回最近 `PANEL_PENDING_LIMIT=200` 条，`pendingTotal` / `pendingBatches` 仍为全量计数。
- **[待做]** 大批量 `pending/` 的启动保护：候选超过阈值时延迟解析（先只读目录名与 mtime，打开时再解析），避免 5k 候选拖慢启动。
- 验收：一个 50 份文档的样例批次，跑完产出 ≤ 150 条候选，面板可按批筛选、批量批准 50 条。

### P1：按业务域分库 + 蒸馏改造

- 把现有客户/业务线映射成 core workspaces 与 `core_id` 上级链（配置层，无需新代码）。
- `distill` 从「逐条」改为「按主题抽样」（新增 `distill.topic_batch_size`，默认 30）。
- 近重复检测加**分桶预筛**（同 type + scope + 标题 token 签名），避免两两比较。

### P2：> 20k 的派生索引

- `storage.index: auto|memory|sqlite`；`node:sqlite` 不可用或版本不符时回退内存。
- 启动校验三件套（条目数、最近 mtime、索引版本），不匹配后台重建。
- 验收：100k 条下 P50 < 120ms、常驻堆 < 200MB、重启不重建。

## 8. 需要先确认的问题

1. **真实规模**：公司 Hub 现在大约多少条知识、多少份来源文档？目标规模是多少（1 万 / 5 万 / 20 万）？
2. **来源形态**：材料主要是 Markdown/Word/PDF/Excel、Confluence/Jira、还是 git 仓库？这决定 chunk 与抽取提示词怎么写，以及要不要先做格式转换。
3. **边界**：公司资料能不能落到本机 Hub？是否需要脱敏/只读副本/按项目隔离？
4. **优先级**：先做 P0（批量萃取工作流）还是先做 P2（>20k 派生索引）？

## 9. 不做的事

- 不做「一键全自动入库 + 自动批准」：违反人工审批硬规则，也会把错误结论固化。
- 不为检索引入向量库：中文 BM25 + 分域已经够用，且与「文件即真相、零联网依赖」冲突。
- 不在 100k 规模下继续用单一大库 + 每回合全库预检。
- 不把「萃取」做成摘要生成：摘要是文档级的，知识是判断级的，两者混在一起会让审批无法收敛。
